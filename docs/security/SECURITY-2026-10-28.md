# Correcciones de seguridad — 28 de octubre de 2026

Revisión del código local y pruebas con PostgreSQL temporal. No se ha conectado a una base remota ni aplicado cambios en producción. El directorio no tiene repositorio Git: no se ha podido revisar el historial.

## Fallos corregidos

| Área | Evidencia anterior | Corrección |
| --- | --- | --- |
| Portadas de otros equipos | Un organizador podía borrar una imagen ajena sin evento asociado, aunque estuviera pendiente de guardar en otro formulario. | RLS limita el borrado al propietario, gestores del mismo equipo y superadministradores. También restringe el listado autenticado de imágenes ajenas. |
| MFA en Storage | El propietario podía borrar sus imágenes con una sesión AAL1 mediante la API directa. | La política exige AAL2 también al propietario. |
| Portadas en uso | Una URL con `?v=2` o `#preview` eludía la comprobación de uso. | La comprobación ignora consulta y fragmento antes de comparar la ruta. |
| Invitaciones | La RPC aceptaba una sesión cuyo correo no estaba verificado. | Exige `email_confirmed_at` antes de conceder la pertenencia al equipo; el rechazo no consume la invitación. |
| Enlaces de autenticación | Sin URL configurada se utilizaba `X-Forwarded-Host`, controlable desde la petición. | En producción se exige un origen HTTPS explícito; se rechazan credenciales, rutas, consultas y fragmentos. El fallback de desarrollo solo admite hosts de loopback y nunca usa la cabecera reenviada. |
| Dependencias | npm audit informó de tres paquetes afectados: Vite (alta), Vitest y @vitest/mocker (moderada). | Vitest 5.0.5 y Vite 8.3.5 en el lockfile. El mínimo declarado de Vitest también se actualizó. |

La explotación de enlaces manipulados dependía además de la lista de redirecciones permitidas en Supabase. La nueva validación elimina esa dependencia para elegir el origen. La comprobación de correo protege sesiones sin verificar; Supabase debe mantener activada la confirmación de correo, ya que desactivarla marca los correos como confirmados automáticamente.

## Activación en un despliegue existente

1. Aplicar `supabase/migrations/0020_security_hardening.sql` después de las migraciones 0001–0019. Es idempotente y no borra datos ni archivos. Publicar solo el código Next.js no actualiza las políticas de Supabase.
2. Configurar `NEXT_PUBLIC_SITE_URL` con el origen HTTPS real, por ejemplo `https://fastpass.example`, sin rutas ni parámetros. Mantener ese origen en la configuración de redirecciones de Supabase y desplegar el código y el lockfile juntos.
3. Mantener activada la confirmación de correo de Supabase Auth.

La limpieza de una portada cuyo propietario ya se ha eliminado puede quedar denegada a otro organizador porque ya no existe la pertenencia que demuestra que compartían equipo. En ese caso se conserva el archivo; un superadministrador con MFA puede eliminarlo si no está en uso.

## Verificación

- Antes de corregir: las nuevas pruebas reprodujeron cuatro fallos de Storage, uno de invitaciones y ocho de validación del origen.
- Después: **190 pruebas aprobadas en 19 archivos**, incluidas RLS real, separación entre equipos, MFA, invitaciones, aforo y concurrencia.
- TypeScript y ESLint correctos.
- Compilación de producción correcta con modo demo desactivado para ese proceso, sin modificar `.env.local`.
- `npm audit`: **0 vulnerabilidades conocidas** en el árbol completo; resultado en `npm-audit-all.json`.
- Escáner local: 184 archivos de código revisados, sin coincidencias con sus patrones de secretos. Esto no verifica credenciales locales ni historial.

Las pruebas de Storage usan un esquema mínimo compatible para ejecutar las políticas reales sobre PostgreSQL; no sustituyen una prueba de la API de almacenamiento del proyecto desplegado. No se ha verificado la configuración remota de Auth, hosting o políticas adicionales que pudieran existir allí. El aviso de Vite sobre el futuro cargador de configuración no afecta a la ejecución actual.
